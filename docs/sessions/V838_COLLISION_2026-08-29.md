# Two different files both called v8.38 — and A24 is in neither

Found 2026-08-29 while checking whether the Claude project's copy of the
v8.38 core was safely duplicated on this PC before deleting it to free
project capacity. It was not, and the reason is worse than a missing copy.

## The measurement

| file | bytes | sha256 (12) | declares |
|---|---|---|---|
| `covenant_unified_v8.py` (deployed) | 551,342 | — | v8.37 |
| `pending-v8.38/covenant_unified_v8.py` | 559,515 | `d3a0ca17030a` | **v8.38** |
| `pending-v8.38/covenant_unified_v8.PROJECT-8e04a293efd9.py` | 558,246 | `8e04a293efd9` | **v8.38** |

The third file is the Claude project's `covenant_unified_v8.PENDING-v8.38.py`,
copied here on 08-29. It had existed only in the project. It is 1,269 bytes
smaller than the pending-v8.38 file already on disk and hashes differently,
and **both call themselves v8.38**.

`d3a0ca17030a` is the hash `docs/results/SWEEP_COMPARISON_2026-08-29_linux.txt`
recorded as "candidate ... v8.38 (pending-v8.38)". So the sweep that cleared
v8.38 green cleared the disk file, not the project one.

This is exactly the condition `test_p18_version_collision.py` was written to
catch — two sources claiming one version — and it went unnoticed because the
two copies lived on different sides of the project/PC boundary, where no
check looks.

## A24 is in neither

`claude/ONE_COMMAND.md` states: "A24 landed in the project as v8.38 and A24b
as v8.39; neither was propagated." Checked by grep against all three cores:

| symbol | v8.37 deployed | v8.38 disk | v8.38 project |
|---|---|---|---|
| `_fair_share` | 0 | 0 | 0 |
| `_compact_locked` | 0 | 0 | 0 |
| `last_eviction_age_seconds` | 0 | 0 | 0 |
| `buffer_pressure` | 0 | 0 | 0 |
| `evicted_under_pressure` | 0 | 0 | 0 |

Controls on the project file, so the zeros are not a failed grep: `def ` 292,
`COVENANT` 93, `evict` 6, `pressure` 8, 9,973 lines, parses under `ast.parse`.

**The A24 anomaly-buffer fix is not in any core on this machine or in the
project.** `test_a24_anomaly_eviction.py` (also rescued on 08-29, and also
project-only until then) asserts every one of those symbols, so it cannot
pass against anything that currently exists. The claim that A24 "landed in
the project as v8.38" is not true of the file in the project under that name.

So the anomaly buffer still evicts oldest-overall on the running nodes — the
condition A24 was written to close is open, and the record said it was fixed.

## What this does not settle

Not measured here: what the 1,269-byte difference between the two v8.38 files
actually is. A diff is an attended job — the two files must not be merged by
guess, and neither should be deleted. Nothing was overwritten: the project
copy landed under a new name carrying its own hash.

## Next

1. Diff the two v8.38 cores and decide which is the candidate. Whichever wins,
   the loser must stop calling itself v8.38.
2. Then decide where A24/A24b actually are — a fourth core, an unmerged
   branch, or never written. `test_a24_anomaly_eviction.py` is the spec either

3. `test_p18_version_collision.py` scans the real tree. It cannot see the
