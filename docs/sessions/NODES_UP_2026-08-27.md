## What blocked the launch, in the order it blocked

### 1. `MANIFEST.sha256` carried a phantom (G1)

Line 3 was `e3b0c442…b855  4]` — the sha256 of the empty string, for a
zero-byte file named `4]`. It can never hash again, so G1 had become a
**permanently BLOCKED gate**, and G1 is the one gate between this bundle and a
launch.

Cleared by measuring, not asserting. All five "changed" files were **clean
against git HEAD**, committed in the same day's two P9 commits; the manifest
was written at 04:11, the commits landed at 12:24–12:29. G1's own FIX text says
a changed file is *either an edit you meant or a delivery that did not land* —
git answered which. Then `verify_bundle.py --write`. Old manifest kept at
`_to_delete/MANIFEST.sha256.PRE-2026-08-27-ONE`.

**Also fixed, and it was armed by me:** `ONE.bat` writes `ONE_RUN.txt` into this
folder, and hashing a launcher's own report is the LAUNCH_CHECK.json deadlock
verbatim (M48) — every run would guarantee the next run reported "changed" and
refused. `ONE_RUN.txt`, `ONE_RETEST.txt`, `ONE_RUN_cloud.txt`, `ONE_RUN_pc.txt`,
`ONE_RETEST_gates.txt` and `ONE_UP.txt` are now in `verify_bundle.py`'s
`OUTPUTS`, and `_to_delete` / `_stage` in `SKIP_DIR`. **Adding a launcher that
writes a report here means adding its report to that list, always.**

### 2. `verify_deploy.py` carries a SECOND, hardcoded delivery list

G1 green, and the restart still refused — correctly. `verify_deploy.py` has its
own four-entry `MANIFEST` frozen in source at the v8.37 build, and it expected
`run_all_tests.sh` = `55016a9d1836` against `836bd0832b68` on disk.

Disk is byte-identical to git HEAD, changed by two commits that landed after the
freeze — `0741b89 Stop the test sweep deleting node identity keys` and
`5517b64 P9: make the policy-file owner-only check platform-correct` — and both
are covered by suites that passed on **both** platforms today (k1 20/20, k3
16/16). Updated, with that evidence written into the file beside the hash.

**The shape worth naming.** `run_all_tests.sh` is a test runner. It is not node
source and cannot change what a node executes, yet a stale hash for it refused
a node restart outright. That list is frozen in source, so it goes stale on
every commit touching one of its four files. That is the third instance of one
disease in a single day — the manifest phantom, the transcript-in-manifest
deadlock, and this. **A delivery check that must be hand-edited to stay true
will eventually be hand-edited to stay quiet.** Derive it from the tag or
commit being deployed.

## Two /health warnings that are false, on all three nodes

Both are live right now and both are wrong. Neither harms the chain; both are
the "a permanent alert trains its reader to skim" failure (M34) — and one of
them is stated as its own opposite.

### `ethics gate has no provider key and is failing CLOSED -- this node will reject every transaction`

Source, `covenant_unified_v8.py:7284`:

    keyless = "quorum(" in judge_id and not insecure and not any(
        os.environ.get(v) for v in ("ANTHROPIC_API_KEY", "OPENAI_API_KEY", "GOOGLE_API_KEY"))

It tests for a **cloud API key** and infers "no judge". These nodes run a local
judge that needs no key. Their own boot line:

    [ollama-judge] qwen3:8b via http://127.0.0.1:11434/v1/chat/completions
                   | OllamaJudge | think=off, constrained JSON, temp=0
                   | fail-closed, insecure mock OFF

So the machinery built to announce "this node cannot do its job" is announcing
it on a node whose ethics gate is wired, reachable and fail-closed. `keyless`
also feeds `degraded`, which is the capability signal a monitor keys off — and
A24's own S9e pins `degraded` as capability, not weather.

Stated precisely: the *condition* is provably computed from cloud env vars alone
and ignores a reachable local judge. Whether transactions are in fact accepted
is a separate empirical question and **has not been tested here** — nothing was
submitted to the live chain.

Fix shape: ask the judge whether it is reachable, do not ask the environment
whether it has a key.

### `node minted its OWN genesis -- it cannot converge with peers…` (node A only)

Source, `:7286`:

    own_genesis = chain[0].transactions[0].sender_pubkey == this node's public key

A is the node that minted the canonical genesis in the first place, so
`genesis.json`'s first transaction is signed by A's key. A then correctly adopts
that shared genesis — and still matches. **The founding node will warn that it
cannot converge, for ever, precisely because it is the source of the genesis
everyone converged on.** B and C are silent only because the key is not theirs.

Measured refutation: all three databases carry genesis `00009b31c6c654d7`, which
is `genesis.json`'s hash, and the same tip.

Fix shape: compare the chain's genesis hash to the canonical genesis file, not
the signer to self.
