## The one conflict, and how it was resolved

`fix/tally-counts-failures-as-passes` conflicted with `main` on
`run_all_tests.sh`. The two changes did not actually disagree: `main` had added
**exactly one line** (`run test_k3_p9_owner_only_guard.py 60`), while the branch
rewrites the file to remove the phantoms and stop the tally counting failures as
passes. Both were wanted.

Resolved by rule — take the branch's file, restore the K3 line after the K1 line
— and then **verified before committing**, because an auto-resolution that is not
checked afterwards is a guess with a commit message:

    VERIFIED: K3 present, and all 38 named suites exist on disk.

If either half had failed, the merge would have aborted and `main` would have
kept everything merged before it.

## Two mount lessons worth keeping

**Git writes cannot go through the file bridge.** The mount cannot delete files,
and git deletes a `.lock` after every ref write — so each git write succeeds and
then poisons the next with *"Another git process seems to be running"*. That is
why `git_setup.py` runs on Windows and clears stale locks first (refusing any
lock under 60 s old, which might belong to a live process).

**And this project caused one of those locks itself.** `covenant_one.py` called
plain `git status`, which *refreshes the index* and therefore takes
`.git/index.lock`. An aborted run at 19:36 left a zero-byte lock that blocked
`git rm` two hours later. Now fixed to `git --no-optional-locks status` — the
same flag the Linux kernel uses in `scripts/setlocalversion`, for the same
reason: *"This script must avoid any write attempt to the source tree."* A
read-only check has no business taking a write lock.
