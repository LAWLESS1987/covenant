## Two health warnings that are false on a correct setup

`/health` came back `degraded: true` with two warnings — while admitting a
transaction and blocking three thefts. Both are false positives, and I can now
point at the lines.

**"ethics gate has no provider key and is failing CLOSED — this node will
reject every transaction"** (line 6142):

```python
keyless = "quorum(" in judge_id and not insecure and not any(
    os.environ.get(v) for v in ("ANTHROPIC_API_KEY", "OPENAI_API_KEY", "GOOGLE_API_KEY"))
```

It tests for an environment variable. It never checks whether a judge is
reachable, or working. A local judge that is functioning perfectly trips it
every time. `NO_API_KEY_LAUNCH.md` predicted this; the transfer above proves
it — the claim "will reject every transaction" is simply wrong here.

**"node minted its OWN genesis — it cannot converge with peers that did not
adopt the same genesis file"** (line 6144):

```python
own_genesis = chain[0].transactions[0].sender_pubkey == self.node.public_key(...)
```

It tests **who minted the genesis**, not whether *this node* minted it.
Node A runs `nodeA_prod.db.key`, a copy of `covenant_A.db.key`, which is the
key that minted `genesis.json`. So adopting a genesis your own founder key
created sets the flag. Node A then converged with node B anyway, which is what
the warning says cannot happen.

**Why this matters more than either warning.** Line 6185:

```python
"degraded": bool(keyless or insecure or own_genesis or self.node.crisis_mode)
```

Two of the four inputs to `degraded` are false on a correct keyless
single-founder setup. So the node reports degraded permanently, and you learn
to ignore it — which is exactly when `insecure` or `crisis_mode`, the two that
are real, stop being visible. That is the same silent-failure class
`HANDOFF.md` §9.3 names as the worst one in this codebase.

Not fixed here. It is a health-reporting change, small and contained, but it
is still a change to shared code and deserves a diff you read.

## What is still off

**Server-side Ollama tuning did not apply.** Ollama was already running when
`covenant_go.bat` started, so it never inherited the tuned environment. The
per-request settings — `num_ctx`, `num_predict`, `temperature=0`,
`keep_alive` — are in every request body and *are* active, which is why you
got 16.7 s and STABLE determinism. Flash attention, `q8_0` KV cache and
`num_parallel=1` are not. Run `ollama_tune.bat`, then quit and restart Ollama
from the tray to pick them up. Worth maybe 10–20%, not another 4×.

**`qwen3.6:latest` is invisible to your running Ollama.** Its 23.94 GB of
blobs sit in `C:\Users\<user>\.ollama\models`, but `ollama list` shows only
`qwen3:8b` — the running server is using a different models directory. So that
24 GB is dead disk. It could not have run on 16 GB anyway.

**Founder key.** Two copies now exist: `covenant\_keybackup\` and
`%USERPROFILE%\.covenant-keys\` (the launcher made the second). Both are on
the same disk as the original. Move one off the machine.

**Unchanged and still true:** the gate is shown `tx.data` only — never
`tx.amount`, never the counterparties. It judged "a human-origin transfer",
not "10 units". Mainnet stays gated: `xrp_testnet_proof.json` does not exist.
